# Day 41: Idempotency

## 🎯 Goal
Understand how to make distributed systems robust against retries and duplicate messages.
**Focus**: "At-least-once" delivery semantics and preventing double-charging.

---

## 🧩 Key Concepts

### 1. What is Idempotency?
*   **Definition**: An operation is idempotent if applying it multiple times has the same effect as applying it once.
*   **Math**: `f(f(x)) = f(x)`.
*   **Examples**:
    *   `x = 5` (Idempotent). Run it 100 times, x is still 5.
    *   `x = x + 1` (Not Idempotent). Run it 2 times, x adds 2.
    *   `DELETE /user/123` (Idempotent).
    *   `POST /pay` (Not Idempotent - usually).

### 2. Why do we need it?
*   **Network Failures**: Client sends request -> Server processes it -> Network dies before response. Client thinks it failed and **Retries**.
*   **Message Queues**: Kafka/RabbitMQ guarantee "At-Least-Once". Your consumer *will* occasionally receive the same message twice.
*   **Result without Idempotency**: User is charged twice. Email sent twice.

### 3. Idempotency Key
*   A unique ID generated by the client (e.g., UUID) sent with the request header `Idempotency-Key`.
*   Server stores this key. If it sees it again, it returns the *stored response* instead of processing again.

## 💻 Code Simulation: Idempotent Payment

Simulating a payment processor that handles duplicate requests gracefully.

```python
class PaymentProcessor:
    def __init__(self):
        # In a real DB, this would be a Unique Constraint Index
        self.processed_txns = set()
        self.balance = 1000

    def process_payment(self, idempotency_key, amount):
        print(f"Incoming: Charge ${amount} [Key: {idempotency_key}]")

        # 1. Check if Key exists
        if idempotency_key in self.processed_txns:
            print("   ⚠️  Duplicate detected! Returning previous success.")
            return "SUCCESS (Cached)"

        # 2. Process Actual Logic
        self.balance -= amount

        # 3. Store Key (Atomic with Balance update)
        self.processed_txns.add(idempotency_key)

        print(f"   ✅  Charged. New Balance: ${self.balance}")
        return "SUCCESS"

if __name__ == "__main__":
    p = PaymentProcessor()

    # 1. User clicks 'Pay'
    key = "txn_abc_123"
    p.process_payment(key, 100)

    # 2. WiFi blips, App retries automatically
    print("-- Retry --")
    p.process_payment(key, 100)

    # 3. User makes a NEW payment
    p.process_payment("txn_xyz_789", 50)
```

**Output:**
```
Incoming: Charge $100 [Key: txn_abc_123]
   ✅  Charged. New Balance: $900
-- Retry --
Incoming: Charge $100 [Key: txn_abc_123]
   ⚠️  Duplicate detected! Returning previous success.
Incoming: Charge $50 [Key: txn_xyz_789]
   ✅  Charged. New Balance: $850
```

## ⚠️ The Trap: "I'll check then write"
*   **Trap**: `if not db.exists(key): process()`
*   **Race Condition**: Two requests come at the exact same time. Both pass the check. Both process.
*   **The Fix**: Use Database **Unique Constraints**. Let the DB enforce uniqueness.
    *   `INSERT INTO payments (id, ...) VALUES (...)`. If it fails with "Duplicate Key", handle it as an idempotent success.

## ⚡ Flashcards

1.  **Who generates the Idempotency Key?**
    *   The **Client**. The server cannot generate it because the retried request would look like a new request to the server.
2.  **Is `PUT` idempotent?**
    *   Yes. `PUT /users/1` with `{name: "Alice"}` sets the state. Doing it twice is same result.
3.  **Is `POST` idempotent?**
    *   No. `POST /users` creates a new user every time. Unless you implement an Idempotency Key mechanism.
